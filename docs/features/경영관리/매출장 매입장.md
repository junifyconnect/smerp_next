# 매출장 매입장 🟢

품의서 승인 시 자동 생성되는 매출장/매입장(원장)을 조회·관리한다. 2026-04-22 PR #14로 **SalesLedger(영업) + MABilling(MA) UNION 통합 조회**가 구현되어 MA 원장이 집계에서 누락되지 않는다(BUSINESS_RULES §10.1). `isActive` 필터, revise 체인 추적, 출처 역참조 필드, 매입 유형 분류(INVOICE/CASH/CARD/IMPORT) 모두 완성. 전용 프론트엔드 페이지만 남아 있다.

**진행률** ██████████████████░░ 90%

## 제공 기능

- **매출장 통합 조회** — SalesLedger(영업) + MABilling(MA, salesAmount>0) UNION, 카테고리/매출처/담당자/결제상태/기간 필터, `isActive=true` 기본
- **매입장 통합 조회** — PurchaseLedger(영업) + MABilling(MA, purchaseAmount>0) UNION
- 개별 원장 상세 조회 및 수정 (PATCH)
- 연체 업체 조회 (매출장 기준, isActive=true + PENDING/PARTIAL + 예정일 경과)
- 결제 상태/예정일 관리
- 영업/MA 구분 breakdown (`summary.salesApprovalCount` / `summary.maBillingCount`)

## 완료

- ✅ 매출장/매입장 목록 조회 API — **SalesLedger + MABilling UNION** (PR #14)
- ✅ `lib/ledger/normalize.ts` — `SalesLedger`/`PurchaseLedger`/`MABilling` → `UnifiedSalesEntry` / `UnifiedPurchaseEntry` 변환 (source 필드 `SALES_APPROVAL` | `MA_BILLING` 포함)
- ✅ 요약 집계 — `salesApprovalCount` / `maBillingCount` 분리 표기 + 합산 공급가/VAT/총액
- ✅ 카테고리 필터에 MA 지원 (`category=MA` 전달 시 MABilling만, `상품`은 Ledger만)
- ✅ 개별 매출장/매입장 상세/수정 API (PATCH — 결제 상태 등)
- ✅ 페이지네이션 (통합 결과에 in-memory offset/limit 적용)
- ✅ `isActive` 기반 revise 추적 — 목록 GET 기본 where에 `isActive: true` 하드코딩, 연체/통계도 일관 적용. MABilling도 동일.
- ✅ `cancelledAt`/`cancelReason` 필드 지원 (revise 시 `REVISED_v{n}` 값 기록)
- ✅ `sourceProductId`/`sourceItemId`/`approvalVersion` 역참조 필드 (원장 → 원본 품의서 행)
- ✅ 매입장 특수 유형 (INVOICE/CASH/CARD/IMPORT)
- ✅ 연체 업체 조회 API (결제예정일 경과 + 미결제 + `isActive: true`)
- ✅ 연체일수 자동 계산 + 업체별 연체 합계 집계

## 남은 것

- ❌ `app/(main)/management/sales-ledger/` 매출장 목록/상세/편집 페이지 (영업+MA 통합 뷰)
- ❌ `app/(main)/management/purchase-ledger/` 매입장 목록/상세/편집 페이지
- ❌ 결제 상태 편집 UI (PENDING/PARTIAL/PAID 전환, 결제일 입력)
- ❌ 연체 필터 UI (기존 `overdue` API 연동, 연체일수 기준 정렬)
- ❌ 외상매출금 대시보드 섹션 (업체별 미수금 합계, 연체 경고)
- ❌ 비활성화된(isActive=false) 원장의 이력 조회 UI (cancelReason 표시)

## API 엔드포인트

- `GET /api/management/sales-ledger` — **SalesLedger + MABilling UNION** (category/clientCompany/managerName/paymentStatus/기간/search 필터, isActive=true)
- `GET /api/management/sales-ledger/[id]` — 매출장 상세
- `PATCH /api/management/sales-ledger/[id]` — 매출장 수정
- `POST /api/management/sales-ledger` — 매출장 수동 등록 (품의서 외 경로용)
- `GET /api/management/sales-ledger/overdue` — 연체 업체 (isActive=true + PENDING/PARTIAL + 예정일 경과)
- `GET /api/management/purchase-ledger` — **PurchaseLedger + MABilling UNION** (isActive=true)
- `GET /api/management/purchase-ledger/[id]` — 매입장 상세
- `PATCH /api/management/purchase-ledger/[id]` — 매입장 수정
- `POST /api/management/purchase-ledger` — 매입장 수동 등록

**주요 라이브러리**: 없음

**의존성 서비스**: PostgreSQL (Prisma — SalesLedger, PurchaseLedger, MABilling). 원장 생성 트리거:
- 영업: `app/api/sales-approvals/[id]/sign/route.ts` (CEO 서명 시)
- MA: `app/api/ma-approvals/[id]/sign/route.ts` (CEO 서명 시 MAContract + MABilling 트랜잭션)

**핵심 난제 (메모)**:
- UNION 조회는 현재 in-memory 병합 + 정렬 + 페이지네이션. 데이터량 커지면 DB View 또는 UNION ALL raw query로 최적화 고려.
- 모든 집계 쿼리에 `isActive: true` 필수. 과거 버전 조회 시 명시적으로 `isActive: false` 분기 필요.
- MABilling의 `salesAmount`/`purchaseAmount`는 MA 품목의 매출/매입 금액을 주기별로 월할당한 값. 계약 월이 아니면 0일 수 있으며, 매출장/매입장은 각각 해당 금액 > 0 인 행만 노출.

- `lib/ledger/normalize.ts` 신설 (UnifiedSalesEntry/UnifiedPurchaseEntry + LedgerSource)
- GET 응답에 `summary.salesApprovalCount` / `summary.maBillingCount` 추가
